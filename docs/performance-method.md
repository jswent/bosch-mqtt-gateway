# Full-pipeline performance measurement

`uv run python dev/benchmark.py` measures the running development stack: Mode 2 TLS simulator, gateway, Mosquitto with TLS and QoS 1, and Home Assistant's MQTT integration. Start and bootstrap that stack first, including Home Assistant authentication. Never run this benchmark concurrently with `dev/e2e.py`, container restarts, or another event injector. It changes simulated point states only.

The default workload sends one 600-point burst followed immediately by ten rounds of 600 point transitions: 6,600 expected state changes. Each point toggles from its actual initial Home Assistant state. Each round waits for every corresponding `state_changed` event before reusing a point, so correlation by entity and target state is unambiguous. A dedicated WebSocket receiver runs throughout injection. Sixteen concurrent HTTP requests drive the simulator; each response carries the simulator's actual `time.time_ns()` timestamp immediately before its TLS event write. This is a high-rate HTTP-driven burst, not 600 events emitted at exactly the same instant.

Pipeline latency is Home Assistant `new_state.last_updated` minus the simulator's emission timestamp. These timestamps share the Docker VM clock. HTTP request scheduling and delivery before simulator emission are excluded from latency. HTTP and host scheduling limit offered load and are included in round wall time and the reported delivered-events-per-second rate. This benchmark therefore does not establish the maximum sustainable wire throughput. Negative latencies fail the run rather than masking clock skew.

Percentiles use nearest-rank p50, p95 and p99 over all individually correlated transitions; the maximum is also reported. Results separate the initial burst from sustained rounds. Every round requires all 600 deliveries within 60 seconds. Before/after authenticated gateway metrics must show no queue overflow, reconnection or failure, and readiness must remain true at the end. The gateway's own publish latency measures only part of the path and is not substituted for end-to-end latency.

The ignored `dev/generated/benchmark-results.json` contains aggregate and per-round results. `dev/generated/benchmark-samples.json` contains each simulated entity, target state, emission timestamp and HA update timestamp for independent reanalysis. Generated Home Assistant and diagnostic credentials are read from files and never printed. Results are specific to the local Docker host, pinned compose images, current source build and HTTP injection concurrency. Real panel timing, network distance, RF sensor delay, and storage/CPU contention require separate measurements in the target deployment.

The runner drains outstanding QoS 1 acknowledgements before its final counter snapshot, since HA can emit a state event before the gateway receives PUBACK. It includes the gateway's internal publish latency metrics for comparison; those metrics retain only the latest 4,096 observations, so their percentiles cover a different window from the full 6,600-event pipeline distribution. `--max-p99-ms` controls a regression gate (default 250 ms); a failed threshold still saves measurements, then exits unsuccessfully. This is a commissioning/regression threshold, not a hard-real-time guarantee.
